**本轮沉淀的方法论**（写代码之外最值钱的部分）：

1. **显示层 ≠ 请求层**：「界面显示 X」不等于「请求发给 X」——用户报障先读浏览器
   存储取证（LevelDB 可直接解析），再决定修哪层。v2.44.2 用 10 分钟定位了
   前两轮都没看到的真因。
2. **prompt 的强迫条款是幻觉温床**：「必须是 N 类之一」+ 白名单装不下真实内容
   = 模型必硬套。给白名单加兜底层（经验记录体）比加「不许幻觉」的口头禁令有效。
3. **测试假绿第三变种**：`ok(cond, msg)` 误用——`ok()` 只收消息，失败被打印成
   「✅ false」但不计数。变异验证是唯一可靠的探测器。
4. **账号归属要落进数据**：采集记录不带「这是谁的」，任何后续判断无从校验。
   web_session 指纹比对 > DOM 抓昵称。

## 二、三条主线（迭代方向）

### 主线 A · 可靠性还债（近期最优先）

静默失效是这个产品最贵的失败形态：用户只会说「不好用」，说不出哪一步断了。
把「证明它能跑」体系化：

1. **E2E 冒烟固化**。本周排查反复用的是同一套技术栈（`--load-extension` +
   CDP + 真实 Service Worker），但每次都是一次性脚本。固化为 `dev/e2e-smoke.mjs`：
   真 Chrome 加载扩展 → 绑定（mock 数据）→ 采集（fixture）→ 激活 → AI（mock 端点）
   → 断言界面状态。注册为第 37 道闸。
2. **新闸门补三类缺口**：HTML 重复 id 检查（dcDiag 事故）；storage.get 返回形状
   lint（禁止数组解构，not iterable 事故）；加载态唯一性（双转圈事故）。
3. **真机验收五项清单化**。`AGENTS.md` 验收边界里列的 5 项离线验不了的
   （绑定带登录态 / noteId 真实命中率 / 过滤后列表 / 定时跨休眠 / AI 真实耗时），
   每项在真机跑一遍并记录到 `docs/真机验收.md`，作为商业化前置条件。

### 主线 B · 数据价值深化（产品主线）

从「采集 + 一次性诊断」走向「数据随时间产生复利」，让 90 天历史真正被用起来：

1. **单篇明细增强**：按曝光/CTR/涨粉排序、低样本过滤、「同类中位数」对比列
   （比值计算一律走 `dcRatio()`，缺失值 `-` 永远不当 0）。
2. **趋势与基线**：趋势 sparkline 从 7 天扩到 90 天；每项指标自动算环比并
   用一句话解读（模板化文案，不给模型编数字的空间 —— `plan-test` 的防骗断言思路）。
3. **选题闭环**（核心增量）：诊断的 actions → 一键转「内容计划」条目 →
   发布后勾选 → 下次采集自动回收该篇效果 → 反哺下次诊断。
   这是「运营工具箱」区别于「数据看板」的关键一环。
4. **对标监控增强**：竞品更新频率/爆文率的周报摘要；爆文预警（阈值来自用户自己
   的基线，不用拍脑袋常数）。
5. **数据出口（读接口）**：把「采到的数据」变成可被外部程序读的稳定接口，
   分三种出口、按依赖递增交付 —— ① 快照导出（扩展内按钮，零依赖）② 本地推送
   （可选 `dev/rpa-bridge`，默认关）③ Agent 工具（MCP / OpenAI tools，供本地
   模型与工作台调用）。**这一条不是产品运行时能力**：扩展本身仍然零 daemon，
   bridge 属于随仓库交付的本地集成工具（`dev/` 下，不打包进扩展）。
   设计见 `docs/rpa/数据接口与Agent衔接设计-2026-10-18.md`。
   为什么值得做：数据留在 storage 里只能人眼看，导出/接口化之后才能接
   「分析 → 矫正 → 日报 → 飞书/企业微信」，也是把工具从「看板」变成
   「每天自动告诉你该做什么」的前提。

### 主线 C · 商业化阶段一（按 `docs/rpa/商业授权设计.md` 执行）

前置条件：**主线 A 的真机验收五项全绿**。在「本地额度计数只是提示」的现状下
收费等于把校验交给可改的客户端，所以顺序不能颠倒。

1. 授权服务器：签发 / 续租 / 额度签名下发（设计文档 3.1 / 3.3 的 L2）。
2. 设备密钥 challenge-response，租约与设备绑定。
3. 客户端切换：`license.js` 加服务端租约校验分支，离线宽限期沿用 72h 设计。
4. 支付与自助激活流程（发货 → 邀请码/ license 文件 → 激活）。
5. 分发评估：Chrome Web Store 上架（审核周期、host_permissions 宽度、
   「不上传数据」承诺的合规表述）。

**明确仍不做**（沿用 AGENTS.md 对标影刀的决策）：元素库、流程编排/拖拽、
魔法指令、通用爬虫、任何需要外部 daemon 的形态。评估新能力先看那张表。

## 四、工作方式（每一轮都一样）

1. **选题**：用户实测反馈优先（本周 5 个 bug 全部来自真实使用截图），issue 走 `gh` CLI
   （`docs/agents/issue-tracker.md`），打 `ready-for-agent` / `ready-for-human`。
2. **测试先行**：新能力先写行为断言（沙箱实跑，不是源码 grep）；修 bug 必须先让一道闸变红。
3. **视觉先实验室**：改 UI 先在 `dev/preview.html` 定稿（`#面板/状态/模式`），
   `SHOT_PAGE=prod` 实拍生产页验收，实验室与生产同构。
4. **全量闸门**：`node dev/verify.mjs` 全绿才算完（36 道，随里程碑增长）；
   新闸门必须做反向验证（改坏 → 红 → 改回）。
5. **真机冒烟**：每次发布前 `node dev/xhs.mjs ping → collect → history` 三连，
   加上设置页激活一次的目视检查。
6. **发布**：版本号四处同步（manifest / README badge / 实验室 LAB_VERSION /
   更新日志）→ 分主题提交 → 推送 GitHub → `node dev/sync-mirror.mjs` 回同步镜像。

## 五、风险与对策

| 风险 | 对策 |
|---|---|
| 单人维护、总线因子 = 1 | 闸门 + 本文档 + 更新日志就是「第二个维护者」；关键决策全写进仓库不靠记忆 |
| 小红书改版导致解析失效 | 解析闸门按中文文案定位（不靠类名下标）；`xhs.mjs collect` 是探针，「页面结构不匹配」错误必须如实冒出 |
| 商业化后「数据不上传」承诺失效 | 授权服务器只收「账号 ID + 设备公钥 + 签名」，笔记数据永远不出本机 —— README 承诺文案随阶段一同步改写 |
| E2E 依赖 Playwright 浏览器路径（机器相关） | 路径进环境变量，缺省值只作提示；闸门在无浏览器环境如实报「跳过」而不是假绿 |
| 数据出口把数据带出本机，与「不上传数据」承诺冲突 | 接口**默认关闭**且只监听 `127.0.0.1`；bridge 是用户自己起的本地进程，不是我们托管的服务；飞书/微信只推聚合结论，不推原始笔记与封面；README 承诺文案随 v2.46 同步补一句「可选本地导出」 |
